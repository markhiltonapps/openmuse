Owner's asks (from concept pictures of a round watch): (1) animate Neddy when he looks things up (book, jetpack flames), (2) record on the watch
and send to the phone afterwards, (3) watch faces, (4) control Neddy's frame rate; plus a small menu that fans out from a button. Owner's answers:

the watch's OWN storage (no microSD required; a card may extend it); a menu rather than new taps; the round board arrives in 1-2 weeks, so either order.

Board facts (Waveshare docs): ESP32-S3R8, 8 MB OPI PSRAM, 32 MB flash, TF (microSD) slot, 2 microphones (ES7210), QMI8658 IMU, PCF85063 RTC on battery,
AXP2101 PMU. PWR button = GPIO10 (high while pressed); holding it ~6 s powers off in hardware.

Built today (step 1, committed locally, not pushed):
- Menu: the PWR side button (short press, toggles) or a swipe up from the bottom edge opens two big tiles in the card area: Animation (saver / normal /
  smooth, cycles on tap) and Screen off (dark and not drawing until any touch, press or words). Closes on a tap beside the tiles, the button again, or 15 s.
  Swiping sideways does nothing while it is open. No Power off tile yet: the AXP2101's software shutdown bit was not confirmed from documentation.
- Animation speed: saver ~8, normal ~16 (as before), smooth up to ~30 frames a second (the listening rate stays low so the microphone is never starved).
  Server setting `animation` (saver|normal|smooth, voice via manage_devices, idle fact `fps` 0/1/2); a change made on the watch is sent as
  {"type":"device.setting","key":"animation","value":N} and kept, so voice and menu agree.
- Test line (NEDDY_IDLE_DEBUG 1 in this build): "... b<pct> <s1> <s2> f<frames last second> r<ms to draw one>": real frames a second and draw cost on the chip.
- Tests: touch_test 52 checks (menu, swipe up, tiles, timeout, screen off, frame rate per level), ui_sim 0 odd windows (frames m1/m2), server device tests 18 pass.

Plan for the rest (decisions to confirm with owner as each starts):
- Look-up animation: server marks a tool running ("looking up"); watch shows a book + flame flicker; drawn in code or real art (owner OK with the animation
  but not at the expense of battery/recording: only while a look-up runs, never while recording).
- Watch faces: current info face + analog + big digital/neon; swipe or voice or menu tile; always-on mode (dim, redraw once a minute); IMU wrist-raise wake.
- Recording: 2 h = 7,200 s into ~22-24 MB of flash means about 24 kbps (about 3 KB/s): a speech codec (Opus ~24 kbps or 3-bit ADPCM at 8 kHz), a custom

  Wi-Fi off while recording, upload after Stop to the api as pieces of a meeting (existing meetings pipeline: transcript, notes, shows in the app), deleted from

=== Look-up animation, watch faces, recording (owner: "push it... build the record, watch face and look up animation") ===
Look-up animation: server sends card {kind:"lookup", on} when the first real tool starts on a watch call (voice-brain.ts, QUICK_WATCH_TOOLS excluded) and off when it
  finishes/errors/aborts; the watch draws Neddy with a book + flickering flames (code-drawn, no art files), eyes sweeping, stops by itself after 45 s, only while looking up.
Watch faces: info (default), analog, neon digital. Menu tile cycles them; voice/chat setting `face`; the idle fact carries it. Neon colour is orange (not yet confirmed with owner).
Recording (menu > Record), on the watch's own flash (no SD needed):
  - neddy_rec.h: IMA ADPCM 4-bit at 8 kHz, 512-byte slots (8-byte header + 504-byte block = 125 ms), quiet slots left out (positions kept so the server puts the silence back),
    written to partition "rec" as it goes; END mark at stop; power-loss recovery by slot ids. Tested on a PC with flash that behaves like real NOR (firmware/tools/rec_test.cpp,
    17 checks, 0 bits set back to 1, 29 dB SNR on speech-like sound).
  - partitions.csv (sketch folder; Arduino Flash Size 32MB): nvs, app0 6 MB, rec 0x19F0000 (about 26.4 MB) = 53,112 slots = 1 h 51 of nonstop speech (more with pauses).
    The first test on the real board must read "[rec] partition ... bytes" in the Serial log (set DEBUG_SERIAL 1) or look at the Record tile: "Up to 1 h 50".
  - Sketch: Record tile -> recBegin (Wi-Fi OFF while recording, BOOT/touch-talk blocked, REC screen with time, time left, storage bar, big Stop; dims after 20 s, any touch wakes it
    without pressing anything); Stop -> Wi-Fi back -> sends in 64 KB pieces (PUT /api/device/recording/<id>?offset&final&started, resumes via GET), "Sent" screen with OK.
    A copy is marked SENT on the watch only when the server answers done:true. A recording left behind (power lost, no Wi-Fi) is sent 20 s after the watch is up and idle.
    After 3 failed turns: "Couldn't send it yet" + Try again; the PWR button leaves that screen (never while recording or sending).
  - Server: device-recordings.ts (decode with silence restored, ffmpeg MP3, Meetings.importRecording -> normal write-up), tests/device-recordings.test.ts (5 pass, decoder equals ffmpeg's).
Checks this session: ui_sim 0 odd windows; touch_test 68 checks; rec_test 17 checks; sketch syntax-checked against stub headers (not compiled for the real board).

=== First real-board test (owner's report) and fixes ===
Owner on the real watch: Stop button did nothing, Watch face tile showed no change, battery unreadable/no charging sign, test line too small to read. Fixes (not yet re-tested on the board):
 - Stop/OK didn't work: the touch chip reports NO position once the finger is up and the sketch passed (0,0); the recorder screen compared that with the press position, so no tap
   was ever a tap. Now the screen remembers the last position and the sketch hands over the last position too. The PC test now lifts fingers at (0,0) like the board (it failed 2 checks, then passed).
   Second way to stop: the PWR button (the screen says so).
 - Watch face tile: it did change the face, but the menu stayed open and the idle face only returns after 10 quiet seconds, so nothing seemed to happen. Now the menu closes and the new face shows at once.
 - Battery: big (64x32 outline, 28 px text), colour by level, bolt + "charging" / "plugged in", red at 15%, and "No battery 00 01" with the raw status bytes when the chip can't be read (it showed nothing before,
   so the reading was failing). The sketch now switches on the chip's battery/USB measuring and battery detection (regs 0x30, 0x68), reads volts (0x34/0x35), falls back to volts for percent,
   and detects charging from either charger bits. Unverified: tell me what the screen says (percent, charging, or "No battery xx xx").
 - Frame rate: Smooth measured 17 fps (draw 11 ms): the idle microphone read waits 20 ms every turn. It is now read every 120 ms (IDLE_MIC_EVERY_MS; 0 = old behaviour). Test line is off (NEDDY_IDLE_DEBUG 0).

=== Second board test: no battery connected, upload fails ===
Owner's photos: watch has NO battery (screen showed "No battery 20 15": USB power present, no battery, so the reading was right); a 1-minute recording waited on the watch and "Couldn't send it yet".
Railway's request log shows NO request from the watch to /api/device/recording, so the upload failed on the watch before reaching the network. Likely cause: the leftover recording was sent
while the watch's normal secure connection to Neddy (websocket) was still open; two TLS connections at once can run the chip out of memory. Fix: the connection to Neddy is closed before an
upload and not restarted until it is done (recBeginSend, loop's `uploading`); the failure screen now shows the reason ("status -1, mem 41k" = what failed and the largest free memory block).
Battery with no battery: now plain text, "Plugged in, no battery" (or "No battery"), no empty icon, no raw numbers. Real-board result still needed: does the upload now go through? Tell me what the failure screen says if not.

=== Look-up animation never appeared (owner: weather, temperature, time zone questions) ===

already switched off and never came back. Now speaking does not end it; it ends when the server says the look-up is over (sent before the answer is read), when he is spoken to again, or after 45 s,
and a look-up in progress keeps the idle face from taking over. Note: questions answered without any tool (a time zone he knows) never signal a look-up; weather is a fast tool, so the book shows only a second or two.
