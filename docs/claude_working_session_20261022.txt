RECORDER SAFEGUARDS (2026-10-23, owner: "build both safeguards")
-----------------------------------------------------------------
Why: on Oct 23 a 15-minute meeting was lost. The bucket rejected the api's keys, every audio piece got a 502
for 15 minutes, the phone kept the pieces only in memory and the app showed nothing; at Stop the server had no
audio ("No sound reached the server"). Last night's meeting (115766b3) most likely hit the same fault.
1) Keep the audio on the device until the server has it
   - apps/mobile/src/meeting-store.ts: IndexedDB (memory fallback). Each 30 s piece is saved before sending and
     removed once the server has it.
   - apps/mobile/src/meeting-uploader.ts: sends in order, retries with waits (and at once on "online" / app back),
     resumes after a reload, closes the recording on the server only after every piece arrived (job kept on
     the device), keeps pieces the server refuses as "closed" (stuck) so they can be saved as a file, clears
     leftovers after 14 days, lets go of a meeting the server doesn't know.
   - meeting-recorder.ts now hands pieces to the uploader (no queue of its own); Stop waits up to 60 s, then
     keeps the rest on the device (or sooner: "Keep it on this device and carry on").
2) Warn within seconds
   - After 3 failed sends in a row (about a minute in: the first 30 s piece is sent at 30 s): "Not reaching the server" card in the recorder, "· not sending" on the red
     bar, a status line for screen readers, and in the Saving sheet the card + the keep-and-go-on button.
   - The meeting's page shows "Still sending from this device" (about N minutes left, Save a copy of the
     audio) or, when the server had already closed it, "Part of this recording couldn't be sent".
3) Server (apps/server/src/meetings.ts)
   - start() saves and removes a tiny test file first: with storage refusing files no recording starts (503,
     plain words). chunk() answers a refused piece with a 503 in the same plain words (was a bare 502).
Help: new topic "A recording says it isn't sending" (shot recordertrouble, light + dark, marks 1-3) and a line in
"Record a meeting". help-shots.mjs has a recordertrouble shot (fake recorder, server that refuses pieces).
Tests: tests/meetings.test.ts (+1: start refused, piece 503, works again), apps/mobile/test/meeting-uploader.test.ts
(8). Browser check (Chromium, fake microphone, a server that refuses pieces) passed 9 of 9: warning within about 10 s,
audio kept in IndexedDB, sent and removed after recovery, Stop with unsent audio kept it and did not finish early,
a reload sent it and then told the server the recording was over.
Known limits: audio kept only in this browser (a different device can't send it); a recording the server closed
after 45 minutes without any piece can't take late pieces (kept for Save a copy); a phone that locks stops
sending until the app is back; native (non-web) apps don't record meetings yet.

WATCHES: ALREADY THERE, NOW ALSO IN PLAIN WORDS (2026-10-23)
I told the owner "tell me only if" watches were a new idea; they weren't: watch_page / Goals > Tracking already watched a public
page for change, text or a price drop, with no model per look. Added a fourth condition, "describe" (value = the person's words,
"the medium is back in stock"). Code: watch-judge.ts (prompt, parseVerdict, steadyText, limits), engine/service.ts (judgeDescribed,
judgeWatch, canJudgeWatches, readingsResetAt, observe), agent.ts (schema, MIN_DESCRIBE_MINUTES = 15), agent-ui.tsx (form option,
card line "Right now: ..."), conversation.ts (watch_page wording), Help topic watch-page (shot watchdescribe), neddy.html.
How it behaves: the model reads the page only when its words (clocks and dates removed) changed since the last reading, at most 12 a
day per watch, never more often than every 15 minutes (the form defaults to 60). Told when the words come true (even if already true
on the first look), and again only after it stopped being true and came true again. A garbled answer or a model error isn't counted
and is tried again; a sign-in wall/captcha/error page is said once ("I can't read this page"), not taken as "not yet"; no model on
the server: refused when the watch is created. The daily limit counts a UTC day; the card gives the restart time in the person's zone.
Review (visual, usability, copy) signed off after two rounds. Known gaps (not built): no chat/voice tool to stop or edit ANY watch
(a repeated watch_page makes a duplicate); no debounce of a flapping yes/no/yes; the Recent checks table still says "Changed / No
change" for described watches; the form offers "Something I describe" even when the server has no model (the save says why); the
card line can read "Right now: Not yet: ...".
Lesson: an edit that leaves a parse error (a straight apostrophe inside a single-quoted string) then run through `biome --write`
rewrote two unrelated lines (the create_routine tool). Check `git diff` after any biome run that followed a syntax error.
